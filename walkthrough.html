LEDGERAPP · BEFORE
The original route permanently erased data
// Hard DELETE from transactions const { rowCount } = await db.query( 'DELETE FROM transactions WHERE id = $1', [req.params.id] ) res.json({ message: 'Transaction record permanently erased' })
Audit finding
A financial event, amount, type, description, and timestamp disappeared permanently.
The same pattern existed in users and accounts. There was no recovery route, audit route, or deletion timestamp.

LEDGERAPP · CHANGE 01
Add a timestamp instead of destroying the row
deleted_at TIMESTAMPTZ DEFAULT NULL -- Active means deleted_at IS NULL -- Retained evidence has a timestamp UPDATE transactions SET deleted_at = NOW() WHERE id = $1 AND deleted_at IS NULL
Schema decision
Users, accounts, and transactions all receive deleted_at because all three have recovery or compliance value.
recoverableauditabletimestamped

LEDGERAPP · CHANGE 02
Normal reads hide history; audit reads reveal it
// Product path SELECT * FROM transactions WHERE account_id = $1 AND deleted_at IS NULL; // Audit path SELECT * FROM transactions WHERE deleted_at IS NOT NULL;
Routes added
/transactions returns active rows only.
/transactions/audit/deleted intentionally returns retained deleted rows.
/transactions/:id/restore recovers a row by setting deleted_at back to NULL.

LEDGERAPP · CHANGE 03
Performance and compliance trade-offs are documented
CREATE INDEX idx_transactions_active ON transactions(account_id) WHERE deleted_at IS NULL; 24 months × 10,000 transactions/month = approximately 240,000 rows 80% active = 192,000 active rows
TRADEOFFS.md
Soft delete fits financial history, recovery, and foreign-key relationships.
Hard delete remains appropriate for ephemeral tokens, temporary caches, and verified erasure workflows.
An auditor can query retained rows and use deleted_at as evidence of when the record left normal views.
